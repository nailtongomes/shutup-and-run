# Agents

Notes for an AI coding agent in this repository. Decisions live in [docs/DECISIONS.md](docs/DECISIONS.md). What the operator agrees to lives in [docs/CONVENTIONS.md](docs/CONVENTIONS.md). Behavior for callers is in [README.md](README.md).

## Build and test

```bash
cargo fmt --all -- --check
cargo clippy --all-targets --locked -- -D warnings
cargo test --locked
shellcheck scripts/*.sh
```

`scripts/install.ps1` and `scripts/shutup-and-run.bat` have no linter in CI. The `.bat` is ASCII with CRLF line ends (`.gitattributes`). Keep it short and keep its checksum logic the same shape as `install.sh`.

The Windows `.exe` (`src/wsl.rs`, the WSL2 supervisor) is built on `windows-latest` in CI with the MSVC toolchain. From Linux it cross-compiles for a check, with `rustup target add x86_64-pc-windows-gnu` and `apt-get install gcc-mingw-w64-x86-64`:

```bash
cargo clippy --all-targets --locked --target x86_64-pc-windows-gnu -- -D warnings
cargo build --release --locked --target x86_64-pc-windows-gnu
```

The parts of `src/wsl.rs` that shell out to `wsl.exe` and `schtasks.exe` can only run on Windows 11 with WSL2. Their pure parts (flag parsing, `wsl --list` decoding, the rendered config, checksum matching) are unit tested everywhere. `tests/poll-mock/poll_mock.py` is a stand-in poll URL for tests, and `tests/poll-mock/cycle.sh` runs it against a worker in CI. `tests/windows-sandbox/run.ps1` is a hand test in Windows Sandbox, as a user who is not an administrator, of `install.ps1` and the logon task; it cannot run WSL2. `shutup-and-run wsl doctor` on a machine without WSL must stop at its first line and exit 1; CI checks that on a Windows runner.

`docs/INTEGRATION-CONTRACT.md` and `docs/schemas/*.schema.json` are the public contract. `src/contract.rs` holds them to the code: it sends every file in `docs/schemas/examples` through the real router, poll parser and callback, and checks what the runner emits against the schemas. A change to a request field, an answer body, a status code or a poll answer form changes the schema, an example and the document in the same patch. `jsonschema` is a development dependency only. `examples/n8n/*.json` were checked by hand against a local n8n; CI does not run n8n.

The Android binary (a phone in Termux: internet sharing only, `src/android.rs`) links Android's own C library, never a static one: a static binary has no DNS there. It is built with the NDK (`ANDROID_NDK_LATEST_HOME` on GitHub's runners); `tests/internet/termux.sh` runs the x86_64 build in termux/termux-docker, with `scripts/install-termux.sh`, in CI too:

```bash
rustup target add aarch64-linux-android x86_64-linux-android
export $(bash scripts/android-ndk.sh PATH_TO_NDK)
cargo clippy --all-targets --locked --target aarch64-linux-android -- -D warnings
cargo build --release --locked --target x86_64-linux-android
bash tests/internet/termux.sh target/x86_64-linux-android/release/shutup-and-run
```

The release binary is static musl. SQLite is bundled, so the link needs a C compiler and `musl-gcc`:

```bash
rustup target add x86_64-unknown-linux-musl
sudo apt-get install -y musl-tools build-essential
CC_x86_64_unknown_linux_musl=musl-gcc cargo build --release --locked --target x86_64-unknown-linux-musl
```

The GitHub-hosted image already has shellcheck. CI installs `musl-tools` with `scripts/ci-apt.sh`. Each `apt-get` is capped. If it fails, the script leaves `azure.archive.ubuntu.com` and retries against `archive.ubuntu.com`, then `mirrors.kernel.org`.

## Accept and smoke

Needs Docker, and no other container labeled `shutup-and-run=1`.

```bash
cargo build --release --locked
sudo bash scripts/accept.sh target/release/shutup-and-run
```

`SHUTUP_AND_RUN_SMOKE=1` runs all of `scripts/smoke.sh` on that instance. `accept.sh` starts its own process. It does not touch a production `shutup-and-run.service`. Without systemd it runs the binary in the background.

Against an instance that is already up:

```bash
SMOKE_URL=https://127.0.0.1:8787 SMOKE_TOKEN=... bash scripts/smoke.sh
sudo SMOKE_LOCAL=1 bash scripts/smoke.sh
```

The scratch image is the Dockerfile with the musl binary copied to `./shutup-and-run` first. `scripts/size.sh` measures the launcher's RAM and CPU. It is not part of CI. Neither is `scripts/screenshots.sh`, which makes the README's pictures of the local page again (Docker, and node with Playwright); a change to the page runs it. The numbers and the reservation to make for the process are in [docs/SIZING.md](docs/SIZING.md).

## Keep it this shape

- One machine, one bearer token. An allowlist entry is one repository. `repo` allows `repo:tag` and `repo@digest`. It does not allow `repo-evil`, a wildcard, or someone else's image. Do not loosen that match. The one way around the list is `poll_any_image`, which applies to a polled task only, never to a push, and needs `poll_url`. Do not widen it.
- The customer's own work on the PC comes before job throughput. Under `resource_profile = shared-pc` (the default when `worker_os` is `windows`) every container gets a CPU and a memory limit, with swap equal to memory (and, under any profile, a limit of 4096 processes and Docker's `init`), and no job starts while memory or disk is short. A request above the machine's limit is refused, never cut down. Admission is two reads inside the slot lock (`src/resources.rs`), and a pull worker that is short does not poll. No resizing, and a running job is never killed for pressure or because the person came back. The one thing sampled while jobs run is one `docker stats` reading per job every 30 seconds: its CPU throttling, CPU time, memory and network bytes, written to its row as they come and once more when the job ends (`cpu_ms`, `memory_peak`, `network_bytes`); what it wrote to its own layer (`disk_bytes`, Docker's `SizeRw`) is read once, as its container is removed; and while its image downloads, how far (`pull_done`, `pull_total`, cleared when the pull ends). They are for the owner and the operator on the machine; do not put them into the callback or the poll body. `jobs --summary` and the doctor's `ROOM_FOR_MORE_SLOTS` turn them into a suggested `max_job_memory` and `max_slots`; a suggestion never changes a limit by itself. `min_idle_secs` (off by default) is one more admission read: the Windows supervisor writes the idle time to the service's stdin (`src/host.rs`), and a reading that is missing or 45 seconds old does not block.
- Under `shared-pc` every admission also asks `src/safety.rs`: healthy, warning or blocked, from the same cheap reads plus the PC's own memory, CPU use and disk on the host feed. Blocked is mandatory and nothing lifts it; a reading that is missing blocks or warns, never passes. A warning starts a job only with the owner's consent, which is given in three places and no others: the local page (`/local/safety`), `safety authorize` at a terminal, and `--owner-consent` (`wsl install --owner-consent`, `safety authorize --owner-consent`), run at the machine by whoever installs it to record the consent the owner gave in the contract (channel `contract`, every code in `safety::WARNING_CODES`). Do not add another flag, a config key, env var, API field or route that grants it, and do not make the thresholds configurable: they protect the person at the PC from the operator too. A change of substance to the notice is a new `safety::NOTICE_VERSION`. `tests/safety/linux.sh` runs the adverse cases against a real Docker; it is a hand test, not CI. So is `tests/managed/linux.sh` for managed containers (about four minutes: the backoff waits are real).
- `src/lending.rs` holds four more waits for a new job, outside the safety levels: outside `lend_hours`, a Windows PC on its battery below `BATTERY_MIN_PERCENT` (60, a constant), a person presenting or with a program in full screen, and a metered network (`metered` on the host feed, from `GetNetworkConnectivityHint`), which the person at the PC may accept with `lend_on_metered` (open form, off by default). Each stops admission and the poll, never a running job; a feed reading that is missing or stale does not hold. `lend_hours` is a condition on admission, not a scheduler: do not add per-window job lists, a queue for later, or a start at the window's opening. The page, `status` and `status.json` (`lending.resumes_at`) say when the next window opens; that is all it is. On Windows it is read on the Windows clock, from the offset the supervisor sends (`utc_offset_secs` on the host feed); without it, on the clock inside WSL2. The feed also carries the Windows time (`unix_ms`), and the service sets the WSL2 clock to it when they are 5 seconds or more apart (`src/host.rs`); that is the one clock it ever sets, and only toward Windows'.
- Memory (`src/memory.rs`) is diagnosis, never action on the person's programs: the supervisor sends the programs holding the most of the PC's memory only while it is tight (`memory::tight`), and that list lives in the service's memory and on the local page and the local doctor (`MEMORY_HELD_BY_PROGRAMS`, filtered out of `doctor --report`). Do not put it in `status.json`, a log line, the poll body, a callback or a report, and do not add a way to close or signal a Windows program. `status.json` has `memory` with the amount to free and the time waited; `memory_hours` and `memory_waits` keep the lowest memory per hour of the week and seconds waited per day. On a Windows PC the last job's end drops the VM's cache (`memory::give_back`); a Linux machine keeps its cache.
- A pause is the `draining` row in `meta`: `1` until someone resumes, or the second it ends (`pause --for`, the page's 1 hour, 3 hours, rest of the day), after which it is over with nothing to clear. A restart ends only the first kind. No schedule of pauses, and no pause that a request or the poll URL sets.
- The runner executes; it does not orchestrate jobs from outside. A job that was interrupted (`reason` `interrupted`: its container is gone, or stopped non-zero while the worker was not running) is reported once through its own `callback_url` and never started again. A callback is the same body sent until one `2xx` or one hour; do not add a second callback field, a retry of the job, or workflow state.
- On Windows the supervisor holds a shutdown only through Windows' own screen (`WM_QUERYENDSESSION` on a window that is never shown, `ShutdownBlockReasonCreate`), only while a job runs, answering from the cached status line. It stops no job until `WM_ENDSESSION` says the session is really ending. No dialog, toast or service of its own.
- `%UserProfile%\.wslconfig` is the user's and covers every WSL2 distribution. The install writes it only when it does not exist and no other distribution does (or the operator named a size). An existing file changes only through `wsl limits --apply`, which keeps every other line and a `.wslconfig.bak`. `wsl uninstall` removes it only when the install wrote it, its sha256 still matches `wslconfig.sha256`, and no other distribution is left. Nothing in the program runs `wsl --shutdown`.
- Certificate passthrough is the one mount there is. It is a machine setting the owner turns on, on the machine, with `certificate_consent`; it gives every container the same two read-only files at fixed paths, from per-job copies that are removed at the job's end. Do not add a per-request switch, a path a request can choose, an API route for it, or the password to any config key, log line, job row, callback, status or report. PKCS#12 is parsed by the `openssl` program, not by a crate. `src/certificate.rs`.
- `job validate`, `demo` and `config check` go through the worker's own code: `launcher::check_request`, a `Launcher` on a throwaway history, the doctor's checks. Do not give any of them a second copy of a rule or a way around the allowlist. Every doctor check has a stable `code`; add a code, never rename one.
- A request sets image, env, command, timeout, cpu, memory, and shm. It does not set mounts, ports, privileged, capabilities, or a network mode. Do not add those fields. A manifest is that same request, fetched once from `manifest_url`; it cannot point at another manifest.
- A worker polls every 30 seconds at the fastest. `config::MIN_POLL_INTERVAL_SECS` is the one number, also the default. A write of a lower value is refused; a load of one runs on the minimum and warns, and never fails. Do not add a way under it, a test switch included: the scripts wait for real polls.
- The poll body is who is asking and what it could lend: `worker`, `os`, `arch`, `version`, `max_slots`, `free_slots`, `cpus`, `memory_bytes`. Do not put the machine's config, tokens, job history, or a self-reported address in it. The only requests to the poll URL besides a poll are the probe of `config check` (the same body with `free_slots` 0 and no token) and the one of `internet on --discover`, sent once when the person turns internet sharing on, which asks where the relay is (`"lend": "internet"`, schemas `internet-discovery-*`).
- A Linux machine is the owner's and trusted. A Windows machine is a client's PC and is not: assume its user can read the poll token and every task's env. The poll URL decides which machines get work.
- No `schema_version` and no register call. A request is not versioned; the poll body's `version` is how a server tells releases apart. Enrollment is the first poll with a token the server has not seen.
- Unknown JSON fields and unknown TOML fields stay rejected. A machine has one config source: `config.json` (every key, tokens included, mode 600, no environment on top), or `config.toml` plus environment. `poll_token` is not a TOML key; on a `config.toml` machine it is `SHUTUP_AND_RUN_POLL_TOKEN` only.
- `config.json` is written only through `config::save_json`, which validates first. Nothing invalid reaches the disk, and a file damaged some other way must not stop the service (`Settings::load_json` falls back). A new key goes in `config::KEYS`, in `docs/schemas/worker-config.schema.json`, and gets a place: the open form, the locked form, or CLI only.
- The agent CLI (`config`, `status`, `doctor`, `jobs`, `managed`, `pause`, `resume`) never asks a question, takes `--json`, and keeps its exit codes: 0, 1 failed, 2 usage, 3 invalid. A line that is not ok carries one next step, `hint` (also printed as `fix`, its name until 0.2.9; one sentence, never two). Nothing it prints, and nothing in `doctor --report`, may carry a secret, or a value of the poll URL's query (`config::mask_query`): those may be a person's tax id or e-mail.
- Every error and warning code has a hint in `src/hints.rs`, in English and Portuguese, and a row in `docs/FOR-AGENTS.md`. A new code gets both in the same patch; a test fails otherwise. The hint is the only place a next step is written: a check names its code and, when the sentence needs it, one detail (`.with(...)` fills the `{}`).
- `jobs` prints when a job ran, how it ended and what it used. Never its env, command, callback or key. What a job printed is kept apart (`src/joblogs.rs`): the last 256 KiB of stdout and stderr, one file per job in `logs/` next to the history, mode 600, written as the container is removed, deleted after 7 days, not masked. Only `jobs logs` and the local page read it (for a job still running, they read the same output from Docker at that moment); it does not go into the poll body, a callback, `status.json` or `doctor --report`. A failure to write it is a warning, never a failed job. No size or retention setting. Docker's own copy of a container's output is capped at two `json-file` files of 5 MB (`bollard_rt::log_config`), a constant like the rest; a container's anonymous volumes go with it; and on Windows the distribution's systemd journal keeps 100 MB (`wsl::JOURNAL_CAP_SCRIPT`, written by the install and every update). Likewise, once a day the images no job used for 30 days go (`Launcher::clean_unused`, `launcher::UNUSED_DAYS`, the `images` table keeps each image's last use); on a Windows PC also the untagged ones, then `fstrim`. Always on, no setting: the PC is the client's and the worker does not leave its leftovers there. It never compacts the WSL2 disk file or makes it sparse (`WSL_DISK_TO_COMPACT` tells a person how).
- On Windows a job is a container inside the `shutup-and-run` WSL2 distribution. The `.exe` is a supervisor; it does not talk to Docker and does not run scripts. No Docker Desktop path, no script mode.
- Every route needs the bearer token, except the local page (`status_page = true`: `GET /`, `/favicon.ico`, and `/local/*`), which answers only a loopback peer naming a loopback host, and a POST only from its own origin. It shows status and the config with secrets masked, and edits `config.json`: everyday keys directly, dangerous keys (`OnPage::Locked`) behind the admin login. It never shows a secret or a job's env; it shows a job's output at `/local/logs`, from the log files; the one env it shows is a managed container's plain `env`, in its editor, behind the admin login. With `screen_view` on (a machine setting, `OnPage::Locked`, off by default), `/local/screen/JOB_ID/` proxies HTTP and the WebSocket to port 6080 of that running job's container, for noVNC, view only (`src/screen.rs`): the address comes from Docker's inspect, never from the request, and a WebSocket needs the page's own `Origin`. Do not let a request, a poll answer or the API turn it on, choose a port or a host, or reach a container that is not that job's. It is in one language at a time, English or Portuguese. Do not put anything else on the port without the token.
- The Windows `.exe` is one console-subsystem program with a static C runtime. The logon task runs it under `conhost.exe --headless`, and every child process is created with `CREATE_NO_WINDOW`. The worker must never show a window.
- Managed containers (`src/managed.rs`) are the one place the worker starts work by itself: `once`, `interval`, `always`. A definition has the fields of a job request and a policy, nothing more; do not add cron expressions, dependencies between containers, mounts or ports. A run goes through `Launcher::launch_managed`, so every admission check of a push applies; do not give it a way around one, and do not turn a refusal into a forced start. Which run belongs to a definition is the `managed` column of its job row.
- Managed mode and push/pull never mix. The mode is a row in the history (`meta`), changed only while no job row is unfinished, in one SQL statement (`Store::set_managed_mode`), and checked in `Launcher::admit` and again in the insert itself. Do not add a second way to start a container that skips `admit`, and do not let the mode change under a running container.
- A managed container's secret values are in the `secrets` column and go only into a container's env. Nothing prints them: not `managed show`, the page, the editor, `status.json`, a log line or a note. There is no API route for managed containers.
- Internet sharing (`src/internet.rs`, `src/relay.rs`, [docs/INTERNET.md](docs/INTERNET.md)) is a mode apart from the worker, for a PC that cannot run containers: its own file (`internet.json`, written only by `internet on`, `off`, `pause`, `resume` and the page's two buttons), its own process (`internet serve`, run by the logon task `shutup-and-run-internet` or the systemd unit of that name) and its own page on 127.0.0.1:8788, which shows it and has two buttons for the person at the PC, pause 1 hour and stop, behind `status::local_only` (loopback, a POST only from its own origin). It runs beside the worker or alone; `fit` says which a PC can lend, and `status` shows both. It needs no Docker or WSL and touches nothing of the worker but reading its `status.json` for a pause. The PC dials out to the operator's relay (`relay`, the same binary; `install.sh` with `SHUTUP_AND_RUN_RELAY_SERVER=1` makes it the systemd unit `shutup-and-run-relay`, and the release workflow pushes it as the image `ghcr.io/nailtongomes/shutup-and-run-relay`; the proxy on Docker's bridge address, never on the internet; `GET /pcs` there, with the relay's token, is the operator's list, never a password or an address); nothing on the PC listens but that page. A new stream waits for the worker's pause, `--hours`, the battery, presenting and a metered network (`lending::hold`), not for memory or safety, and a stream already open is never cut. The PC refuses every destination on its own network (`internet::is_public`, checked on the address it dials): do not add a way around that outside the tests. The password is in `internet.json`, `internet credentials` and the page, nowhere else: not `internet status`, a log line, the status file, the poll body or a report. The operator may choose it (`internet on --login ID:PASSWORD`, or the `login` of the discovery answer); an error about it never repeats the value. Turning it on at the PC is the owner's consent; no request, poll answer or relay message turns it on, and nothing remote pauses or resumes it either. `internet on --discover URL` is that same consent: the URL's answer says only where the relay is, once, at that command. The link is plain TCP, on purpose for the alpha, and the relay accepts any PC unless the operator gives it a token (`relay --token-file`, `internet on --token`); the next steps are in docs/INTERNET.md, in that order. The one data limit is on the PC (`--max-day`), a wait like the others; the relay lets one PC carry `relay::PC_STREAMS` (140) streams at once, a constant. A task reaches a PC through its `env` (`HTTPS_PROXY`, `internet credentials --env`): do not add a proxy field to the request. No allowlist of destinations, multiplexing or second proxy protocol until the owner asks. On a phone (Android, Termux) only internet sharing runs, without root and without an app of ours; it shares only on Wi-Fi unless `--mobile-data`, given at the phone like `--metered` (no discovery answer, relay message or request sets it), and a change of network dials the relay again; its battery, when Termux:API is there (`android::battery`), goes to the same wait as a laptop's. Do not add root, an APK, or a way around the Wi-Fi rule.
- No queue, no scheduler beyond the three managed policies, no web UI beyond that one local page (and internet sharing's, with its pause and stop), no access to it from the network, no second database, no cross-machine coordination, and no automatic restart of a container that exits other than a managed `always` one.
- No secrets, tokens, or credentials in the repo, in examples, or in logs. Do not print `SHUTUP_AND_RUN_TOKEN`.
- Prefer a smaller patch. A shortcut in code is marked `// shortcut: <limit>, <when to upgrade>`.
- A choice a later reader would second-guess goes in `docs/DECISIONS.md`: context, the decision, and what it costs.
- A release is a new `version` in `Cargo.toml` reaching `main`: the `release` workflow builds, creates the tag `v<version>` and publishes. Nobody pushes a tag by hand. So a version bump is the release: bump only when the owner asked for one. `install.sh` on `main` is what that release's one-line install fetches.
